## Замечания и исправления

1. **P2, исправлено: старый курс при reset/Play.** CommandControl.stop может сохранить
   направление предыдущего состояния, затем restart_from_default_state меняет позу,
   а heading hold пытается вернуть старый курс. В момент подключения timeline был
   остановлен, ready=False, цель курса около −75°, робот в spawn.
   В start_go2.py heading hold теперь применяется после инициализации; перед reset
   цель очищается и в reset передаётся обычная команда без старой коррекции курса.
   Добавлен регрессионный тест. После Play на живой сессии цель близка к 0°,
   робот оставался у spawn до запуска маршрута.
2. **P2, исправлено: Esc сохранял множество нажатых ручных клавиш.** После отмены
   следующая клавиша могла снова добавить старую скорость. cancel теперь очищает
   pressed; тест проверяет последовательность UP → Esc → LEFT.
3. **P2, воспроизводимость запуска.** start_factory открывает сцену, а не маршрут.
   Добавлены run_inspection_route.bat / cancel_route.bat и мониторящий CLI.
   Запускатель проверен полным живым маршрутом; транспортный ACK не выдаётся за успех.
4. **Архитектурное ограничение, осталось:** run_route.py содержит абсолютный корень,
   проверку конкретной сцены, лимит пяти приборов; plan_route предполагает проход
   вдоль X. Это препятствует новой цели пользователя — подключать разные площадки.
   Следующий R0 описан в SIM_TO_REAL_ARCHITECTURE.md.
5. **Ограничение sim-to-real, осталось:** KitIO получает точную позу из физического
   движка, а препятствия однократно читаются из USD. Это oracle-адаптер для демо;
   заменять его оценённой позой и сенсорной картой нужно явно, с метками времени
   и статусом локализации. Текущий код не обнаруживает новые препятствия.
6. **Зависимость настройки от FPS, осталось:** интегратор курса в KitIO использует
   настенное dt, физика — время симуляции. При изменении RTF контроллер меняет
   относительную динамику. В R0 разделить часы управления и watchdog.

Область ревью: маршрут, арбитраж, кадры, отчёт, текущие тесты и профиль живой сессии.
Не выполнялись тесты реального SDK, физического робота, новых препятствий и другой
площадки. Полный холодный запуск нового процесса Kit не выполнялся; исправление
callback применено к живой сессии без перезапуска/перезагрузки сцены. prepare_route.py
содержит временный совместимый патч старой сессии; удалить этот механизм после
перехода на стабильный адаптер с версионируемым API, а не расширять hot-patching.

После изменений: 22/22 теста; синтаксис 37 файлов tools/tests проверен;
git diff --check без ошибок пробелов. Установок и изменений системы не было.

## Измерения FPS и ресурсов

Сырьё: `reports/performance_review/{paused,baseline,baseline_resources,policy}.json`.
Значения относятся к живой сцене цеха. Камера и оба видимых окна оставлены включёнными.

| Показатель | Измерение |
|---|---:|
| App FPS, симуляция остановлена, 15 с / 703 обновления | 46.80 |
| App FPS, физика включена, 20 с / 416 обновлений | 20.79 |
| Кадр median / p90 | 45.69 / 57.92 мс |
| RTF, накопленное dt физики / настенное время | 0.416 |
| Физический шаг | 0.005 с, 4 шага на обновление |
| Scope pre→post физики с обработчиками, на кадр | 19.74 мс |
| Runner.step, отдельный 15-секундный замер, на кадр | 4.73 мс |
| Частота render events сенсора при Play | 4.15 Гц настенного времени |
| CPU всей машины, среднее | 85.11% |
| CPU Kit, доля всей машины | 72.58% |
| Среднее максимальной нагрузки логического CPU | 94.27% |
| GPU utilization, среднее | 38.45% |
| VRAM, среднее | 3664 / 8188 МиБ |
| RAM занято / доступно | 19.49 / 12.35 ГиБ |
| Рабочий набор Kit | 5.63 ГиБ |

Ресурсы измерены отдельным близким по времени окном 23 с, а не синхронно с каждым
кадром; приведённые значения не предназначены для точной корреляции отдельных пиков.
Runner.step включает наблюдения/инференс/выдачу целей, это не чистое время нейросети.
Scope физики включает callbacks, его нельзя складывать с runner-временем как
независимые затраты. App FPS не является отдельным измерением GPU frame time.
В paused-замере камера отрисовывается иначе; его частоту нельзя сравнивать с 10 Гц Play.

Текущая конфигурация подтверждена живьём: GPU dynamics=False, broadphase=MBP,
тензоры cpu. Рендер RealTimePathTracing; главный viewport 1280×720, дополнительный
640×360; лимит обновлений 50. Torch intra/inter threads=10/10,
carb/TBB=16/16, physics numThreads=8.

Вывод: признаки ограничения CPU при включённой физике; недостаток RAM/VRAM не
наблюдается. При RTF 0.416 сенсор 10 Гц за секунду симуляции даёт ~4.16 Гц за
секунду реального времени — это объясняет наблюдаемые пользователем ~5 FPS камеры.
Повышение частоты сенсора само по себе не ускорит физику и может увеличить нагрузку.
20.79 FPS соответствует ожидаемому RTF около 20.79/50.

## Что пробовать для ускорения

В этом ревью измерена базовая производительность; ускорение пока не заявляется.
Окно камеры не скрывалось: пользователь отметил важность его частоты.
Физический шаг и частота политики не менялись — они связаны с обучением походки.

Следующий ограниченный эксперимент после согласования:
1. A/B/A на той же позе и сцене: текущие torch intra threads=10 против 1/2;
   межоперационные потоки не менять в работающей сессии. Вернуть исходное значение.
2. Отдельно проверить физические потоки 8 против 4 с корректным жизненным циклом Kit;
   не смешивать с изменением камеры и шага физики.
3. Если CPU-изменения не помогают, Tracy-профиль CPU/GPU для определения ожиданий,
   затем тест рендера/разрешения основного окна при неизменной инспекционной камере.

Каждый вариант: ≥100 кадров, RTF, FPS, p90, загрузка CPU/GPU, затем маршрут и
качество кадров. Рост FPS без сохранения поведения робота не считать улучшением.
Перенос физики на GPU не рекомендован без нового A/B: CPU уже выбран и ранее
давал лучший результат для одного Go2. Новые пакеты/драйверы сейчас не нужны.

Официальная справка по оптимизации:
https://docs.isaacsim.omniverse.nvidia.com/latest/reference_material/sim_performance_optimization_handbook.html
